# 技能：wp-run（執行並留證）

> 來源：`docs/17` 第 4、9 站，`docs/18` 各領域範例；改寫為通用版本。由 `mission-executor` 執行。

**本次交付（由主責提供）：** $ARGUMENTS

參數第一項是工作包編號，其餘是主責這次特有的說明（目的、已知與已排除、特別要求）。主責沒有說明**目的**時，先問一句「這個結果要拿來做什麼決定？」再開始——目的會決定你遇到岔路時往哪邊判斷。

## 先讀

1. 該工作包的 `wp.md`：驗收條件、驗證指令、`scope.paths`、關卡、相依、預算。**狀態必須是已核准**（已合併到主幹）；相依的工作包必須已被接受。不是的話停下來告訴主責。
2. 所屬任務的 `mission.md`（不做什麼、必須由人做什麼）。
3. 工作包引用的介面契約、既有決策、相依工作包的結論。
4. 依 `wp.md` 的 `domain`，使用對應的領域技能：`domain-sw`、`domain-fw` 或 `domain-hw`（`sys`／`research` 依實際動到的內容選用，可多選）。

## 範圍

- 只能修改 `scope.paths` 內的檔案，以及本工作包自己的工作目錄。
- 需要動其他地方：**停下來**，用 `decision-request` 開決策請求（選項通常是「擴大本工作包範圍」或「另開工作包」），列出那些檔案的負責人。
- 不修改介面契約、驗收條件、驗證指令；認為有問題時開決策請求。

## 作法要求

- 在分支 `wp/<WP 編號>-<slug>` 上工作（或依專案約定的命名）。
- 計算與分析寫成可重跑的腳本；每個參數註明來源。
- 引用規格書數值時附文件名、版次、頁碼與條件；找不到的寫 UNKNOWN 並說明缺什麼，**不要估一個數字補上**（之後的人會把它當成規格書的值）。
- **留證（手動模式）：** 每個驗證指令的完整輸出存成檔案（例：`evidence/EV-<WP號>-NN.log`），依 `kit/templates/evidence-manifest.yaml` 登錄：證據編號、對應的驗收條件、指令、結束碼、commit、工作區是否乾淨、輸出檔的 sha256、驗證階、標籤。失敗的執行也保留、也登錄。證據只增不改；重跑產生新編號。
- 你產生的證據標籤**最高是 OBSERVED**。模擬只能支持「模擬顯示」。
- 程式改過之後，舊的證據不可沿用；重新產生。

## 停下來問（開決策請求，不相依的部分可以先做）

- 需要在方案之間取捨，或規格沒寫清楚的行為（例如錯誤時要回傳什麼）。**不要自己選**。
- 驗收條件達不到，或你認為條件本身有問題。
- 需要超出範圍、新增相依、或動到別人負責的領域。
- 同一個問題試了三輪仍失敗，或超過 `budget`。
- 介面契約或既有決策不夠用、互相矛盾。
- 需要實體動作：改用 `human-task` 起草程序書，然後停下。

## 不要做

改驗收條件或驗證指令；刪除、放寬或跳過測試；合併或核准；任何燒錄、除錯器、串列埠、儀器或設備操作；把主機端或模擬結果寫成實機結論；修改範圍外的檔案。

## 完成後

1. 提交（commit 尾註 `WP: <WP 編號>`），依專案約定開 Draft MR／PR，**不要合併**。
2. 用 `review-packet` 產生共讀包草稿。
3. 依 `mission-executor` 的回報格式回報；另外列出「只能在實機確認的項目」（沒有就寫「無」）。
