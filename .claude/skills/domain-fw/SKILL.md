# 領域技能：韌體（domain-fw）

> 來源：`docs/18` §0、§2；改寫為通用版本。由 `mission-executor` 在 `wp-run`、`rework`、`human-task` 中套用。

## 韌體補充規則

- **不執行、也不產生燒錄、除錯器連線、串列埠或儀器的指令。** 實機驗證是人的任務。
- 交給人燒錄的檔案必須由 CI 從已核准的版本產生，不使用你工作區裡的檔案。
- 每個門檻、校正常數、暫存器設定值都要註明來源（介面契約欄位、規格書或參考手冊的文件名、版次、頁碼，或已簽認的量測）。**沒有來源就停下來問**，不要填一個合理的值。
- 主機端測試與模擬的結果不能推論為實機行為。回報中固定列出「**只能在實機確認的項目**」。
- 處理數值時說明資料型別與範圍，檢查溢位、飽和、除以零、定點數的縮放。
- 中斷與主程式共用的資料要說明如何保護。
- 每次回報程式與記憶體用量（Flash／RAM）及與上一版的差異；超過預算就停下來問。
- 保護功能、故障處理、看門狗、開機程序、記憶體配置、更新機制屬於**安全關鍵**：任何變更都要逐項填寫安全審查檢查表（例：`kit/checklists/fw-safety-review.md`），並由合格審查者逐行審查。
- 介面契約（腳位、類比鏈、通訊、電源）不夠用或有矛盾時，停下來問，不要自己改或繞過。

**最常做錯的事：** 把主機端測試通過當成實機可用；常數沒有來源。**最高能驗到：** 模擬（V3）；實機由人。

## 依任務類型的作法

### 數值處理（主機端可完整測試）
- 可調參數做成可設定；預設值不要自己選：列出候選值與各自的取捨，開決策請求。
- 說明每個中間值的範圍並證明不溢位；測試包含最大輸入、最小輸入、劇烈跳變、長時間固定輸入、初始狀態。
- 規格沒寫的情況（例如故障期間該怎麼處理）：列選項問。
- 不要用主機端的合成資料下「實機已改善」的結論；起草給人執行的量測工作包建議。

### 驅動與時序（最多驗到模擬）
- 先說清楚天花板：這類變更的正確性最終只能在實機確認；**不要宣稱時序正確**。
- 每個暫存器設定值註明參考手冊的文件名、版次、章節與頁碼；無法查證的標 UNKNOWN 並列出來。
- 把「硬體相依的薄層」與「可在主機端測試的邏輯」分開；後者用替身寫單元測試。
- 列出中斷與主程式共用的資料與保護方式；說明中斷優先序的理由，不確定就列為問題。
- 列出時序的預期值與允許誤差，並用 `human-task` 起草給人執行的量測程序。共讀包中涉及時序的主張一律標 HYPOTHESIS，指向對應的量測工作包。

### 安全關鍵變更
- 把程式寫得**容易審**，而不是寫得精巧。
- 門檻等數值**只使用人已決定的值**（決策請求編號），在程式中註明來源；你不可以調整數值，認為有問題就停下來問。
- 明確定義並測試每一種狀態轉換，包括開機時已在異常狀態、感測器故障時（無法確認狀態時應視為不安全；現有設計不是如此就停下來問）。
- 保護路徑不可依賴可能被阻塞的工作或通訊；說明它的執行條件。
- 測試涵蓋：剛好在門檻、門檻上下一個最小單位、在遲滯區間內來回、讀值跳變、故障輸入。
- 不要修改或刪除現有的保護測試；需要調整時逐一列出並說明。
- 逐項填寫安全審查檢查表：每項寫結果與依據（行號、證據編號或頁碼），不可只打勾；無法判定的寫「需人確認」。必看清單包含本次所有變更的行。

## 回報時另外包含

只能在實機確認的項目（與對應的人類任務建議）；Flash／RAM 用量與差異；每個新常數的來源；目標編譯是否成功（NOT RUN 時寫原因）。
