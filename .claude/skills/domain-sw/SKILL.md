# 領域技能：軟體（domain-sw）

> 來源：`docs/18` §0、§1、§4；改寫為通用版本。由 `mission-executor` 在 `wp-run`、`rework` 中套用。

## 軟體補充規則

- 只改這次任務需要的地方。看到順手可以改善的程式，寫進回報的「後續建議」，不要動。
- 修錯之前先寫出能重現問題的失敗測試，並保留它。
- 不用空的例外處理、預設值或重試把錯誤蓋掉。錯誤要被回報或明確處理。
- 公開介面、資料格式、設定檔格式的變更屬於 G2：停下來問。
- 新增相依套件前先說明必要性、授權與替代方案，等人決定。
- 效能相關的主張要附量測方式與數字；沒量就不要說「更快」。
- 不把憑證、個資或機密寫進程式、測試資料或日誌。

**最常做錯的事：** 改得比要的多；用例外處理把錯誤吞掉。**最高能驗到：** 預備環境（V4）。

## 依任務類型的作法

### 新增功能
- 解析或處理邏輯要對照介面契約；新增或更新**契約測試**（契約改了而程式沒跟上時，測試要會失敗）。
- 舊版資料或訊框要能照常處理時，說明相容作法並寫測試。
- 排除或丟棄資料時留下可查的紀錄（筆數、範圍），不要無聲丟棄。
- 測試涵蓋：全部正常、部分異常、全部異常、未定義的值。
- 規格沒寫的行為（例如「全部異常時該回傳什麼」）：列選項問，不要自己定。

### 修錯（依序做，不要跳步）
1. **重現**：先寫一個會失敗的測試重現問題。重現不出來就停下來說明試了什麼，不要憑猜測修改。
2. **找根因**：指出程式行號，區分「根因」與「症狀出現的地方」。根因在別的模組或輸入資料時，告訴主責，不要只在輸出端把症狀夾掉。
3. **修正**：修根因、改動越小越好；保留第一步的測試；檢查同類問題是否存在於其他地方，列出來但先不要改。

### 行為不變的重構
1. 動手前先**盤點**現有實作之間的差異（四捨五入、邊界處理、單位等）。差異可能是 bug 也可能是有意的：逐一列出來問主責要保留哪一種，不要自己統一。
2. 主責決定後，先補上鎖住現有行為的測試，確認它們在重構前通過。
3. 重構後同一批測試必須**不改一字**就通過。
4. 重構前與重構後各執行一次完整測試，兩次的輸出都留存並登錄。
5. 公開函式的名稱與簽名保持不變；需要改請先問。

### 介面契約變更（跨領域）
第一步**只做影響分析，不改任何程式**：契約要改的欄位（型別、縮放、範圍、版本）；兩側受影響的檔案與測試；新舊版本混用時會發生什麼與可行的過渡作法；需要哪些領域負責人核准；建議的工作包拆法與先後順序。交影響分析與決策請求（過渡作法由人選）。

## 回報時另外包含

新增與修改了哪些測試（改的是期望值還是測試本身、理由）；有沒有新增相依；有沒有動到公開介面或資料格式；你沒處理的情況。
