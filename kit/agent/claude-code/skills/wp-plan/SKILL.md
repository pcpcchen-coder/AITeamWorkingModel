# 技能：wp-plan（拆工作包）

> 來源：`docs/17` 第 2 站；改寫為通用版本。由 `mission-executor` 執行。

**任務編號：** $ARGUMENTS

## 先讀

- `work/missions/<任務編號>-*/mission.md`（必須已由人核准合併；還沒合併就停下來告訴主責）。
- `knowledge/interfaces/` 下的介面契約、`knowledge/adr/` 的既有決策（若存在）。
- 角色矩陣（例：`kit/team/role-matrix.md` 或專案中對應的檔案），找出各領域的負責人。

## 這一步只規劃，不要開始實作

每個工作包依 `kit/templates/wp.md` 填寫，必須有：
- 領域、執行者（ai／human／pair）、自主度、關卡等級。
- 允許變更的路徑（`scope.paths`），盡量窄。
- 驗收條件：每一條都能被判定通過或不通過，附可執行的驗證方式與驗證到第幾階。涵蓋邊界與異常，不只正常情況。
- 相依的其他工作包。

## 要求

- 每個工作包要小到**一次審查 30 分鐘內**看得完。
- 需要實機才能確認的事，另開「由人執行」的工作包。不要讓主機端測試假裝涵蓋實機行為。
- 燒錄、上電、量測、送板、採購一律排成由人執行。
- 列出每個工作包會動到誰負責的領域。
- 你不確定該怎麼拆、或有兩種拆法的地方，**列成選項問主責**，不要自己選。

## 停下來問

- 任務的成功定義有部分沒有任何工作包能驗證。
- 範圍路徑必然與別人進行中的工作包重疊。
- 有兩種以上合理的拆法。

## 不要做

- 開始實作任何工作包。
- 為了讓計畫看起來完整而寫無法判定的驗收條件（例如「功能正常」）。
- 合併 Plan MR／PR。

## 回報

用 `mission-executor` 的回報格式，並包含：
1. 工作包一覽表（編號、內容、領域、執行者、關卡、最高驗證階、相依）。
2. 你對哪三條驗收條件最沒把握、為什麼。
3. 哪些成功定義目前沒有任何工作包能驗證。
4. 需要主責決定的事。

提醒主責：核准前可以用 `/critique-plan` 請獨立驗證者挑毛病。
