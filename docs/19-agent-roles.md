# 19 — 哪些 AI 介入點需要獨立的 Agent

**文件狀態：** 設計決定與建置規格 v0.7 · 2026-11-17
**回答的問題：** 十三站裡 AI 介入的地方很多，需要每一個都做成獨立的 Agent 嗎？
**結論：** 不需要每個介入點一個。需要的是**四個**獨立 Agent，其餘是掛在它們底下的技能（可重複使用的 prompt）。關卡檢查不應該是 Agent。
**狀態：** Agent 尚未建立；本文是建置規格。Agent 定義檔的格式以所用工具的官方文件為準。
**誠實聲明：** 這是設計判斷，未經試用。四個的切法可能需要依實際使用調整。
**互動示範：** [`demo/workflow-walkthrough.html`](../demo/workflow-walkthrough.html) 的每一站標示了負責的 Agent；「四個 Agent，各管各的」可逐一查看立場、權限與絕不做的事。

## 1. 判斷標準：什麼時候值得拆成獨立 Agent

拆開有成本：每次交接都會掉資訊，多一個 Agent 就多一份要維護的定義。只有符合下列任一條才值得拆：

| # | 理由 | 說明 |
|---|---|---|
| 1 | **需要獨立性** | 檢查者不能帶著作者的脈絡與立場。同一個對話既寫又驗，等於自己改自己的考卷 |
| 2 | **權限不同** | 有的角色只該讀、不該寫。把限制做在 Agent 的工具權限上，比寫在 prompt 裡可靠 |
| 3 | **服務的對象不同** | 執行者為任務主責工作；帶讀的助理為審查者工作。同一個 Agent 兩邊服務會混淆立場 |
| 4 | **觸發方式不同** | 有的由人當下觸發，有的照排程自己跑、不需要任務脈絡 |

不符合任何一條的，留在同一個 Agent 裡當技能就好：例如「規劃」與「執行」由同一個 Agent 做，因為執行時需要規劃時的脈絡。

## 2. 四個 Agent

| Agent | 為誰工作 | 做什麼 | 可以寫入 | 絕不做 | 拆開的理由 |
|---|---|---|---|---|---|
| **執行者** `mission-executor` | 任務主責 | 訪談與起草目標、拆工作包、執行並留證、寫共讀包、返工、準備人類任務的程序書、分析人填的紀錄 | 工作包範圍內的檔案與該任務的工作目錄 | 核准、合併、改驗收條件、碰設備、修改人填的紀錄 | 基準角色 |
| **驗證者** `independent-validator` | 審查流程（不為作者） | 在乾淨環境重跑驗收、核對主張與證據、找驗收條件沒涵蓋的風險；也用同樣的獨立立場審計畫 | 只有驗證報告 | 修改產品程式或測試、替作者補救、給出「核准」 | 獨立性、權限 |
| **共讀助理** `coread-guide` | 個別審查者 | 依必看清單帶讀、回答問題並附來源、出挑戰題、比對見習審查、學習型工作包的助教 | 不寫入 repo；只產生留言草稿給人 | 替人按核准、修改分支、替人送出留言 | 服務對象、權限 |
| **節奏助理** `cadence-reporter` | 整個團隊 | 每日簡報、備援週摘要、每週會議議程、每月案例回顧的材料 | 只有節奏類檔案（摘要、議程、紀錄） | 評價個人、判斷責任歸屬、編造進度 | 觸發方式、權限 |

### 四個之外

| 介入點 | 處理方式 | 理由 |
|---|---|---|
| 關卡檢查（Gate） | **不做成 Agent**；由確定性的 CI 檢查執行。工具完成前用人工檢查表 | 關卡要每次給出同樣的答案，不能交給會變動的模型判斷 |
| 決定、核准、合併 | 人 | 核准的正本是人在平台上的已驗證行為 |
| 合併前自查 | 驗證者的一個技能，僅供參考 | 不取代關卡 |
| 軟體／韌體／硬體的差異 | 執行者的領域技能，不是三個 Agent | 差異在交付內容與規則（見 18），不在立場或權限 |
| 代理主責接手 | 執行者的一個技能 | 接手後就是該任務的執行者 |

## 4. 每個 Agent 的定義必須包含

1. **什麼時候用它、什麼時候不該用它。**
2. **立場：** 為誰工作；與其他 Agent 的關係（驗證者不讀作者的對話紀錄來相信結論）。
3. **工具與寫入範圍：** 以工具權限設定為主；工具無法限制到的部分，明寫在定義裡並在說明文件中列為「靠自律、未被強制」。
4. **絕不做的事**（上表），並附理由。
5. **停下來問人的條件。**
6. **回報格式**（[`handoff-prompts.md` §3](../prompts/handoff-prompts.md)），含「沒做什麼」與「不確定的地方」。
7. **模型建議：** 驗證者建議使用與執行者不同的模型；做不到時至少是全新的對話。這是建議，不寫死特定模型。

所有 Agent 都遵守專案 `AGENTS.md` 的常駐規則（[`handoff-prompts.md` §2](../prompts/handoff-prompts.md)）與領域補充規則（[18](18-domain-handoffs.md)）。

## 5. 這些 Agent 不能保證什麼

- **獨立性是相對的。** 驗證者與執行者若是同一個模型，仍可能有同樣的盲點；真正的獨立性來自 CI 重跑與人類審查（01 §3）。
- **權限限制有邊界。** Agent 定義能限制工具，但能執行指令的 Agent 理論上仍可改檔案。不可逆的限制（不能合併、不能碰設備）必須靠平台權限與執行環境（11 §8.3）。
- **Agent 不承擔責任。** 產出仍視同任務主責的產出（16 §1）。
- **防護 hook 不在這次範圍。** 攔截指令的 hook 屬於 13 的 K4；這次只做 Agent 與技能。

## 6. 與工具開發的關係

這批 Agent 是 17、18 的 prompt 的封裝，**不依賴** `aitw` 指令列工具，用樣板與白話指示以手動模式運作。它比指令列工具更貼近主軸（人怎麼把工作交給 AI），所以先做。

日後 `aitw` 完成時，技能內的手動步驟（例如手動登錄證據）可改為呼叫指令，Agent 的立場與權限不變。這對應 13 的 K4（Agent 整合包）；屆時 K4 的範圍應扣掉本次已完成的部分。

## 7. 驗收（建立 Agent 的工作需達到）

1. 四個 Agent 的定義檔與其技能，格式經對照官方文件確認，並在說明中附上查證的網址。
2. 每個 Agent 的定義涵蓋 §4 的七項。
3. 安裝說明：如何放進一個專案 repo；GitLab 與 GitHub 皆適用。
4. 每個 Agent 至少在一個虛構的小例子上**實際執行一次**，留下過程摘錄與觀察；無法在當下執行的，明確標示 NOT RUN 並給出人可以照做的試用步驟。不可把沒跑過的寫成可用。
5. 列出「靠自律、未被工具強制」的限制清單。
6. 不含防護 hook、不新增相依、不改動既有流程規則。

## 8. 待決與待驗證

- 團隊實際使用哪一種 Agent 工具尚未確認（14 §8 的訪談題）；本規格先以 Claude Code 為對象，立場與權限的設計與工具無關。
- 四個的切法是否合適、技能的粒度是否太細，需要試用後調整。
- 執行者一個 Agent 涵蓋的事很多，若實際使用時脈絡過長，可能需要把「規劃」拆出去。
