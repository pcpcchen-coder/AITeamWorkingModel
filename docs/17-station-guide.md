# 17 — 十三站操作細則與交付 AI 的 Prompt 範例

**文件狀態：** 設計草案 v0.6 · 2026-11-16
**對應：** [互動示範](../demo/workflow-walkthrough.html) 的 13 站。本文把每一站展開成「人做什麼、對 AI 說什麼、AI 交回什麼、人要確認什麼」。
**現在就能用：** 示範頁上的 `/wp-plan`、`aitw …` 等指令是**規劃中的工具**，尚未實作。本文的 prompt 是**今天就能貼給任一 Coding Agent 的白話文字**，搭配 [`kit/templates/`](../kit/templates/) 的樣板以手動模式運作（09 §12）。
**誠實聲明：** 案例、人員、數值皆為虛構。prompt 是依設計推演寫成的範例，**尚未在真實專案上試用**；時間為假設。請把它們當起點，依實際效果修改。
**平台用語：** 以 GitLab 的 MR 為例；GitHub 上讀作 PR。留言指令在 GitLab 用 `aitw:` 前綴（14 §5）。

## 0. 總覽：十三站與九步流程

13 站是 09 §4 的九步流程在一個案例上走兩個工作包的展開。

| 站 | 名稱 | 球在誰手上 | 對應 09 步驟 | 人要對 AI 下 prompt 嗎 |
|---|---|---|---|---|
| 1 | 設定目標與邊界 | 人 | 1 | 是（請 AI 訪談並起草） |
| 2 | 拆解成工作包 | AI | 2 | 是 |
| 3 | 核准計畫，凍結驗收條件 | 人 | 3 | 選用（請另一個 AI 挑毛病） |
| 4 | 執行並留證（硬體分析） | AI | 4 | 是（最重要的一次交付） |
| 5 | 決策請求 | 人 | 4 的支線 | 是（追問、回覆後請 AI 繼續） |
| 6 | 乾淨環境重跑，產生共讀包 | CI | 5、6 | 是（獨立驗證者、共讀包） |
| 7 | 共讀：挑戰題 | 人 | 7 | 是（審查者自己的 AI 帶讀） |
| 8 | Gate：機器檢查核准 | CI | 8 | 選用（合併前自查） |
| 9 | 執行韌體，獨立驗證提出風險 | AI | 4、5 | 是 |
| 10 | 共讀抓到問題 | 人 | 7 | 是（要求返工） |
| 11 | 返工觸及範圍外，再請示 | AI | 4 的支線 | 是（決定後的指示） |
| 12 | 人類任務：AI 準備、人動手 | 人 | 4 的支線 | 是（準備程序書、分析紀錄） |
| 13 | 每週共讀共推會 | 人 | 節奏 | 是（議程、會議紀錄） |

## 1. 交付之前：一次設定好的三件事

每次交付只需要講「這次任務特有的事」，前提是下面三件事已經到位：

1. **常駐規則寫進專案的 `AGENTS.md`。** 不變的規矩（證據標籤、不自己合併、不碰設備、遇到岔路要問）寫一次，Agent 每次都會讀到。內容見 [`prompts/handoff-prompts.md` §2](../prompts/handoff-prompts.md)。
2. **AI 用獨立的機器身份提交，沒有合併權限**（09 §11、14 §5）。prompt 裡寫「不要合併」只是提醒；真正的保證來自權限。
3. **樣板在 repo 裡**（`kit/templates/`），AI 產出的檔案格式才會一致。

寫 prompt 的七個要素、好壞對照、AI 回報格式，見 [`prompts/handoff-prompts.md` §1、§3](../prompts/handoff-prompts.md)。

## 第 1 站　設定目標與邊界

| | |
|---|---|
| 目的 | 讓目標可被檢驗，並劃清 AI 能做與不能做的範圍 |
| 誰 | 任務主責；備援旁聽 |
| 開始前要有 | 一個想解決的問題 |
| 完成條件 | `mission.md` 的 MR 經主責核准合併 |
| 時間（假設） | 20–30 分鐘 |

**人做什麼：** 回答 AI 的問題。這一站 AI 是訪談者與書記，不是決策者。

**對 AI 說的話（範例）：**

```text
我要開一個新任務，請用訪談的方式幫我把目標講清楚，再起草任務目標檔。

背景：電池模組的溫度量測在低溫段誤差偏大，連帶影響低溫的 SOH 估算。

請一次只問我一個問題，依序問：
1. 完成時，什麼可量測的結果算成功？要驗證到哪一階（計算、模擬、實機量測）？
2. 哪些事明確不做？
3. 哪些動作必須由人執行？
4. 你可以自主做到哪裡、做完給我審？
5. 預算與期限？每週我能花多少時間審查？
6. 誰是備援？

規則：
- 你只問問題和整理，不替我決定目標或成功標準。
- 我沒回答或回答不清楚的欄位留空，標示「待主責決定」，不要自己補。
- 問完後依 kit/templates/mission.md 起草，開分支並開 MR，不要合併。
- 最後列出你認為我還沒想清楚的三個地方。
```

**AI 應交回：** `mission.md` 的 MR；三個「還沒想清楚的地方」。

**人要確認：**
- [ ] 成功定義是可量測的，並寫明要驗證到哪一階
- [ ] 「不做什麼」「必須由人做什麼」有寫，而不是空白
- [ ] 沒有 AI 自己補上的目標或數字

**常見失誤：** 成功定義寫成「改善準確度」這種無法判定的句子；忘了寫由人執行的動作，之後 AI 規劃時才發現。

## 第 2 站　拆解成工作包

| | |
|---|---|
| 目的 | 把目標拆成每個都能獨立驗收、獨立審查的小單位 |
| 誰 | AI 規劃；主責觸發 |
| 開始前要有 | 已合併的 `mission.md`；角色矩陣（16 §2.2） |
| 完成條件 | Plan MR 已開，尚未合併 |
| 時間（假設） | 人 5 分鐘下指示；AI 執行 |

**對 AI 說的話（範例）：**

```text
請為任務 M-001 擬計畫：把目標拆成工作包。這一步只規劃，不要開始實作。

先讀：work/missions/M-001-*/mission.md、knowledge/interfaces/ 下的介面契約、
knowledge/adr/ 的既有決策、角色矩陣。

每個工作包依 kit/templates/wp.md 填寫，必須有：
- 領域、執行者（ai／human／pair）、自主度、關卡等級
- 允許變更的路徑（scope.paths）
- 驗收條件，每一條都附可執行的驗證方式與驗證到第幾階
- 相依的其他工作包

要求：
- 每個工作包要小到一次審查 30 分鐘內看得完。
- 需要實機才能確認的事，另開「由人執行」的工作包。不要讓主機端測試假裝涵蓋實機行為。
- 燒錄、上電、量測、送板、採購一律排成由人執行。
- 列出每個工作包會動到誰負責的領域。
- 你不確定該怎麼拆、或有兩種拆法的地方，列成選項問我，不要自己選。

回報：
1. 工作包一覽表（編號、內容、領域、執行者、關卡、最高驗證階、相依）
2. 你對哪三條驗收條件最沒把握、為什麼
3. 哪些成功定義目前沒有任何工作包能驗證
4. 需要我決定的事

開 Plan MR，不要合併。
```

**AI 應交回：** Plan MR（各 `wp.md`）、一覽表、最沒把握的三條、需要決定的事。

**人要確認：** 見第 3 站。

**常見失誤：** 工作包太大（一個 MR 審不完）；驗收條件寫「功能正常」；把實機驗證藏在「測試通過」裡。

## 第 3 站　核准計畫，凍結驗收條件

| | |
|---|---|
| 目的 | 在動手前確認「問對問題」；之後驗收條件不能被 AI 改動 |
| 誰 | 主責；被動到領域的負責人；高風險者加審查者 |
| 開始前要有 | Plan MR |
| 完成條件 | Plan MR 經核准合併 |
| 時間（假設） | 15–20 分鐘 |

**人做什麼：** 審「範圍對不對、驗收條件夠不夠嚴」，不是審作法細節。

**人要確認（這是全流程最值得花時間的一站）：**
- [ ] 每條驗收條件都能被判定通過或不通過
- [ ] 驗收條件涵蓋邊界與異常（端點、超出範圍、斷線、空值），不只正常情況
- [ ] 驗證到的階數夠高；只到模擬的項目有對應的人類任務
- [ ] 範圍路徑沒有過寬；與別人進行中的工作包沒有重疊
- [ ] 需個別啟動核准的工作包（不可逆、實體動作）已標示
- [ ] 總審查量在你與團隊的容量內（16 §4.4）

**留言範例：**

```text
CHANGE: WP-003 的驗收條件只寫「全量程誤差」，請加上表格端點與超出範圍時的行為。
Q: WP-005 為什麼只量三個溫度點？
RISK: WP-002 與丙正在做的 WP-021 都會改 analog.yaml，請先和丙確認先後。
```

**選用：請另一個 AI 挑毛病（新的對話，不是寫計畫的那個）：**

```text
請以審查者的身份檢查這份計畫（Plan MR !2）。你沒有參與撰寫。

請找出：
- 無法判定通過與否的驗收條件
- 太寬鬆、只測正常情況的驗收條件
- 把實機行為寫成可由主機端測試驗證的地方
- 範圍路徑過寬或彼此重疊的工作包
- 任務的成功定義中，沒有任何工作包能驗證的部分

只列問題與所在檔案行號，不要修改任何檔案，也不要提出你自己的新設計。
```

**常見失誤：** 快速核准計畫，把問題留到成果審查——那時修正成本高得多。

## 第 4 站　執行並留證（以硬體分析為例）

| | |
|---|---|
| 目的 | AI 在範圍內完成工作，並留下別人可以重跑的證據 |
| 誰 | AI 執行；主責交付 |
| 開始前要有 | 已核准的 `wp.md`；相依的工作包已接受 |
| 完成條件 | Draft MR 已開；每條驗收條件都有證據 |
| 時間（假設） | 人 5–10 分鐘寫交付；AI 執行 |

**這是最重要的一次交付。** 寫清楚七件事：目的、要做的事、範圍、已知、驗收與證據、何時停下來問、回報格式。

**對 AI 說的話（範例）：**

```text
請執行 WP-002：上拉電阻值的最壞情況計算與模擬。

【先讀】
該工作包的 wp.md、mission.md、knowledge/interfaces/analog.yaml、WP-001 的結論。

【目的】
WP-001 指出低溫段解析度不足可能是主要誤差來源。我要知道改變上拉電阻值
能不能讓全量程誤差落在目標內，以及代價是什麼，才能決定樣板要怎麼改。

【範圍】
只能改 hw/calc/**、hw/sim/**、knowledge/interfaces/analog.yaml，以及本工作包
自己的工作目錄。需要動其他地方就停下來問我。

【已知與已排除】
- 不換 MCU、不改 PCB 佈局（見 mission.md）。
- 候選值先看 10k、22k、33k。

【作法要求】
- 計算寫成可重跑的腳本；每個參數註明來源。
- 規格書的數值要附文件名、版次、頁碼。找不到的寫 UNKNOWN 並說明缺什麼，
  不要估一個數字補上。
- 每個驗證指令的完整輸出存檔，登錄到 evidence/manifest.yaml（含 commit 與
  sha256）。你產生的證據標籤最高是 OBSERVED。
- 模擬只能支持「模擬顯示」，不能寫成硬體已驗證。

【停下來問我】
- 需要在方案之間取捨（例如選哪個電阻值）：列選項、影響、建議，開決策請求，
  不要自己選。等待時可以先做不相依的部分。
- 驗收條件達不到，或你認為條件本身有問題。
- 需要超出範圍。
- 同一個問題試了三輪仍失敗。

【不要做】
改驗收條件或驗證指令；刪除或放寬測試；合併；任何設備操作。

【完成後】
開 Draft MR，依 MR 樣板寫共讀包草稿，並回報：做了什麼、沒做什麼、
每條主張的標籤與證據、未驗證的範圍、需要我決定的事。
```

**AI 應交回：** Draft MR；`manifest.yaml`；共讀包草稿；決策請求（若有）。

**人要確認（此時只需略看，正式審查在第 7 站）：**
- [ ] AI 有沒有停在該停的地方（有決策請求，而不是自己選了）
- [ ] 回報裡有「沒做什麼」與「未驗證的範圍」，不是只報喜

**常見失誤：** 只說「把 WP-002 做完」，沒講範圍與何時該問；沒要求留證，之後無從驗證。

## 第 5 站　決策請求：AI 不自己選

| | |
|---|---|
| 目的 | 需要人判斷的取捨由人決定，且留下理由 |
| 誰 | 主責（或 16 §5.4 指定的決定者） |
| 開始前要有 | AI 開出的決策請求 |
| 完成條件 | 人在 MR 留言決定；決策檔記錄留言連結 |
| 時間（假設） | 5–15 分鐘；時限 G1 兩個工作天、G2 三個工作天 |

**人做什麼：** 看選項與影響；資訊不足就追問；決定後在 MR 留言。

**資訊不足時，追問：**

```text
在我決定 DR-001 之前，請補上：
- 選項 B（33k）在 60°C 時的解析度餘裕是多少？依據是哪一筆證據？
- 兩個選項各自依賴哪些尚未驗證的假設？
沒有依據的地方請寫 UNKNOWN，不要推估。
```

**決定（在 MR 留言，這則留言才是正本）：**

```text
aitw: decide DR-001 A　同意建議；高溫餘裕優先，且 B 依賴外推的低溫容差。
```

**決定後請 AI 繼續：**

```text
DR-001 我已在 MR 留言決定採用 A（22k）。請：
1. 把決定、我的理由、留言連結寫進 DR-001 的 resolution；不要改寫我的理由。
2. 依 A 繼續 WP-002；analog.yaml 的變更屬於跨領域介面變更，請在共讀包列入必看清單，
   並標明軟體、韌體、硬體的負責人都需要核准。
3. 被否決的選項 B 保留在紀錄中，註明否決理由。
```

**人要確認：**
- [ ] 選項之間的差異是實質的，不是 AI 為了有選項而湊的
- [ ] 知道「不決定的話哪些工作會停」
- [ ] 自己的理由有寫下來（之後接手的人靠這個理解）

**常見失誤：** 口頭或在聊天視窗回答，沒有在 MR 留下紀錄；只回「A」沒寫理由。

## 第 6 站　乾淨環境重跑，產生共讀包

| | |
|---|---|
| 目的 | 由 AI 以外的機制確認結果；把成果整理成人讀得懂的一頁 |
| 誰 | CI；獨立驗證者（另一個 AI 對話）；作者 AI 產生共讀包 |
| 開始前要有 | MR 取消 Draft |
| 完成條件 | CI 通過；驗證報告與共讀包已在分支上 |
| 時間（假設） | 人 5 分鐘下指示 |

**CI 做什麼：** 依主幹上凍結的驗證指令，在乾淨環境重跑。工具完成前，由 CI 設定檔直接執行各工作包的驗證指令。

**對獨立驗證者說的話（開新對話；可行的話用不同的模型）：**

```text
你是獨立驗證者，不是作者。請驗證 MR !14（WP-003）。

你沒有參與實作。不要因為作者的說明而相信結論，請自己看程式、測試與證據。

請做：
- 在乾淨的工作區，依主幹上 wp.md 的驗證指令重跑，記錄實際輸出。
- 逐條核對共讀包的主張：它引用的證據是否真的支持這句話？標籤是否過高？
- 找出驗收條件沒涵蓋到的風險（邊界值、異常輸入、與介面契約不一致之處）。
- 檢查測試是否被刪除、放寬或跳過。
- 列出只能在實機確認的項目。

不可以：修改產品程式或測試。你只能寫 review/verification-r1.md。

回報：逐條 PASS／FAIL／BLOCKED 與依據；發現（註明是否在驗收範圍內）；
你沒有驗證的部分與原因。你的報告不構成核准。
```

**對作者 AI 說的話（產生共讀包）：**

```text
請依 kit/templates/review-packet.md 產生 WP-003 的共讀包 r1。

- 三行摘要：改了什麼、為什麼、影響誰。
- 主張表：每條主張附標籤、證據編號、驗證到第幾階、不適用的範圍。
  沒有被 CI 重跑或人類簽認的，不可以標 VERIFIED。
- 必看清單必須包含：安全關鍵路徑的變更、介面契約變更、被刪改或跳過的測試、
  驗收條件變更、驗證者與你結論不一致之處、你標為 HYPOTHESIS 的主張。
  每項指到檔案與行號並估計閱讀時間。你可以多列，不可以少列。
- 把驗證者的發現原文列入，不要替它下結論或淡化。
- 出一題挑戰題：答得出來代表真的理解這次變更最關鍵的地方。
- 寫明回退方式。
```

**人要確認：** 此站不需人工確認；審查在下一站。

**常見失誤：** 讓同一個對話既寫程式又「驗證」自己；共讀包把驗證者的風險發現寫成「已知限制」一筆帶過。

## 第 7 站　共讀：挑戰題檢驗理解

| | |
|---|---|
| 目的 | 讓審查者把時間花在最該看的地方，並確認真的理解 |
| 誰 | 主責、備援、獨立審查者（16 §4.2） |
| 開始前要有 | 共讀包、驗證報告、CI 結果 |
| 完成條件 | 必看清單逐項看過；挑戰題已回答；問題已留言 |
| 時間（假設） | R2：15–30 分鐘 |

**人做什麼：** 先預測、再讀、再回答。可以請**自己的** AI 帶讀。

**對自己的 AI 說的話（帶讀）：**

```text
我是 MR !9 的備援審查者，有 20 分鐘。請帶我讀。

1. 先不要給我結論。我會先寫下我預期這個變更會怎麼做，你等我寫完。
2. 然後依共讀包的必看清單一項一項帶我看：指出檔案與行號，說明它為什麼在清單上。
3. 我問問題時，回答要附來源（檔案行號或證據編號）。找不到依據就說不知道。
4. 最後請出共讀包上的挑戰題考我，不要先給答案；我答完再告訴我有沒有漏掉什麼。

限制：
- 不要替我按核准。
- 不要修改這個分支。
- 把我還沒解決的問題整理成留言草稿，由我自己送出。
```

**回答挑戰題與留言（範例）：**

```text
aitw: understood　模擬只到第三階，而且低溫容差是外推值；要等樣板量測才算驗證。
Q: 高溫 60°C 的餘裕還剩多少？請在共讀包補上數字與依據。
```

**人要確認：**
- [ ] 必看清單每一項都看了（不是只看摘要）
- [ ] 每條結論的標籤與證據相稱
- [ ] 未驗證的範圍我能接受
- [ ] 我能用自己的話說出這次變更最大的風險

**常見失誤：** 只讀 AI 的摘要就核准；請 AI「幫我看有沒有問題」然後照單全收。

## 第 8 站　Gate：機器檢查核准

| | |
|---|---|
| 目的 | 合併前確認證據、範圍與核准都符合規則 |
| 誰 | CI 的 Gate；工具完成前由合併者逐項檢查 |
| 開始前要有 | 人類核准 |
| 完成條件 | 檢查全過，由人類合併 |
| 時間（假設） | 自動；手動檢查約 5 分鐘 |

**工具完成前，合併者的手動檢查表：**
- [ ] 變更的檔案都在工作包宣告的範圍內
- [ ] 沒有動到政策檔、CI 設定、負責人設定
- [ ] 驗收條件與驗證指令和主幹上的一致；有改動則有對應的人類決策
- [ ] 每條驗收條件都有證據；CI 是針對**最新的** commit 通過的
- [ ] 沒有 AI 自標的 VERIFIED
- [ ] 所有決策請求都有人類留言回覆
- [ ] 核准者符合規則（16 §4.1）：人數、角色、領域負責人；核准是在最後一次提交之後
- [ ] 核准者不是 AI 的帳號，也不是 MR 作者

**選用：請 AI 做合併前自查（輔助，不取代上表）：**

```text
請對 MR !9 做合併前自查，依 docs/11 §5.3 的步驟逐項列出：通過或未通過、依據、
未通過時下一步該由誰做什麼。

只讀取，不要修改任何東西。你的自查不代表核准；找不到資料的項目請寫「無法確認」，
不要假設通過。
```

**常見失誤：** 核准之後 AI 又推了新的 commit，卻沿用舊的核准；跨領域變更只有一位負責人核准。

## 第 9 站　執行韌體，獨立驗證提出風險

| | |
|---|---|
| 目的 | 完成主機端可驗證的部分，並誠實列出只能在實機確認的事 |
| 誰 | AI 執行；主責交付 |
| 開始前要有 | 已核准的 `wp.md`；相依的介面契約已定案 |
| 完成條件 | CI 通過；驗證報告完成 |
| 時間（假設） | 人 5–10 分鐘寫交付 |

交付的結構同第 4 站。以下只列**韌體特有**的要求：

```text
請執行 WP-003：韌體改用查表內插換算溫度。

【先讀】wp.md、knowledge/interfaces/analog.yaml（上拉已定為 22k，見 DR-001）、
現有的溫度換算程式與測試。

【範圍】只能改 fw/src/sensors/**、fw/tests/**、fw/tools/**，以及本工作包的工作目錄。
通訊介面（knowledge/interfaces/protocol.yaml）不在範圍內。

【韌體特有的要求】
- 查表由 analog.yaml 以腳本產生，不要手寫數值；產生腳本一併提交。
- 每個門檻與常數註明來源（介面契約欄位、規格書頁碼）。
- 主機端單元測試要涵蓋：表格兩端、表格範圍外的輸入、相鄰區段的交界。
- 提供目標編譯是否成功，以及 Flash／RAM 用量與上一版的差異。
- 列出「只能在實機確認」的項目（例如取樣雜訊、實際轉換時間），不要用主機端測試
  的結果去推論它們。

【絕對不要做】
任何燒錄、除錯器連線、串列埠或儀器的操作。需要實機結果時，寫成給人執行的
工作包建議，並停下來告訴我。

【停下來問我】同第 4 站；另外，如果你發現介面契約本身有問題或不夠用，停下來問，
不要自己改契約或繞過它。

【完成後】同第 4 站。
```

**人要確認：**
- [ ] 回報中有「只能在實機確認的項目」
- [ ] 沒有把主機端結果寫成實機結論
- [ ] 驗證者的發現有被完整呈現（本例：斷線時回傳端點值且不報錯）

**常見失誤：** 測試只測正常範圍；交付時沒說介面契約不可動，AI 順手改了。

## 第 10 站　共讀抓到問題

| | |
|---|---|
| 目的 | 驗收條件都過了，仍由人判斷「這樣夠不夠」 |
| 誰 | 主責、備援、審查者 |
| 開始前要有 | 共讀包（含驗證者的風險發現） |
| 完成條件 | 核准，或明確要求修改 |
| 時間（假設） | 15–30 分鐘 |

**人做什麼：** 回答挑戰題；判斷驗證者提出、但不在驗收範圍內的風險要不要處理。

**要求修改時的留言與交付：**

```text
CHANGE: 斷線與短路必須回報故障，不可回傳看似合理的溫度。
```

```text
MR !14 我要求修改，請返工。這是第 1 次返工（上限 3 次）。

【要改的事】
感測器斷線與短路時必須回報故障，不可回傳表格端點溫度。

【注意】
這件事需要新增驗收條件，而且回報故障可能要動通訊介面。這兩件都不是你能
自己決定的。請先開決策請求，列出作法選項與各自的影響，等我決定後再動手。

【紀錄】
- 保留原本的提交與失敗紀錄，不要改寫歷史。
- 修完後重新留證；程式改過之後，舊的證據不可沿用。
- 產生共讀包 r2，並列出與 r1 的差異。
```

**人要確認：**
- [ ] 我的要求是具體可驗收的，不是「再改好一點」
- [ ] 有沒有牽涉驗收條件或範圍的變更（有的話要走決策請求）

**常見失誤：** 因為「測試都過了」就核准；要求修改卻沒說清楚要達到什麼。

## 第 11 站　返工觸及範圍外，再請示

| | |
|---|---|
| 目的 | 範圍與驗收條件的變更，由人明確授權 |
| 誰 | 主責決定；AI 依決定執行 |
| 開始前要有 | AI 的決策請求（選項 A：擴大範圍；選項 B：拆出新工作包） |
| 完成條件 | 決定已留言；返工完成並通過 Gate |
| 時間（假設） | 決定 5–10 分鐘 |

**決定：**

```text
aitw: decide DR-002 B　變更較小，兩邊可各自獨立驗證。
```

**決定後的交付：**

```text
DR-002 我選 B。請：

1. 在 WP-003 的 wp.md 新增驗收條件 AC4：「斷線與短路時回報故障碼；不回傳溫度值」，
   並附主機端測試作為驗證方式。在執行日誌註明這是依 DR-002 新增的。
2. WP-003 只做韌體內部的偵測與錯誤碼。不要動 protocol.yaml。
3. 另外起草 WP-007（在通訊訊框加入故障旗標，並讓上位機處理）的 wp.md，
   放進一個新的 Plan MR，不要混在這個 MR 裡。它會動到介面契約，請標為跨領域，
   並列出需要哪些領域負責人核准。
4. 提醒我：WP-004 現在相依於 WP-007。
```

**人要確認：**
- [ ] 新增的驗收條件文字是我要的（AI 沒有寫得比較寬）
- [ ] 新工作包有進計畫審查，而不是悄悄併入

**常見失誤：** 為了省事讓 AI「順便一起改」，結果一個 MR 橫跨多個領域，沒有人審得完。

## 第 12 站　人類任務：AI 準備、人動手

| | |
|---|---|
| 目的 | 實體動作由合格人員執行；AI 負責事前準備與事後分析 |
| 誰 | 合格執行者；主責；簽認者（建議非執行者） |
| 開始前要有 | 已核准的人類任務工作包；CI 由已核准版本產生的燒錄檔 |
| 完成條件 | 紀錄完成；結論經人簽認 |
| 時間（假設） | 依實驗而定 |

五個階段：AI 準備 → 人核准啟動（兩人）→ 人執行 → AI 分析 → 人簽認。

**請 AI 準備程序書：**

```text
請為 WP-005（樣板改裝與三點溫度量測）準備程序書與空白紀錄表，
依 kit/templates/human-task-record.md 的 A 段。

執行者是合格人員丙。你不會、也不可以操作任何設備或發出任何設備指令。

必須包含：
- 目的，以及對應哪一條驗收條件
- 待測物編號與硬體版本、要做的改裝
- 要用的韌體檔：必須是 CI 由已核准的 commit 產生的，附檔名與 sha256
- 設備、接線、逐步操作
- 每一步的預期範圍
- 中止條件（出現什麼情況要立刻停）
- 要記錄的欄位，包含儀器的校正編號與環境條件

你不確定的操作細節（例如溫箱需要穩定多久）請標「待執行者確認」，不要編一個數字。
請註明：本程序不取代實驗室的安全 SOP；兩者衝突時以 SOP 為準。
```

**執行者照實記錄；之後請 AI 分析：**

```text
丙已完成 WP-005 的量測，紀錄在 human-task-record.md 的 B 段，原始資料的位置
與 sha256 也在那裡。請分析。

- 資料標為 OBSERVED；與預期範圍比對，計算各點誤差。
- 紀錄中有偏離：溫箱最低只穩定在 -18°C，未達程序要求的 -20°C。請把偏離列入
  必看清單，並明確寫出哪些結論因此不能成立。
- 沒有量到的範圍不要外推。成功定義若無法判定，就標 UNKNOWN。
- 不要修改 B 段（那是人的紀錄）。
- 產生共讀包，建議下一步（例如補量），但由我決定。
```

**人要確認：**
- [ ] 程序書經合格人員審過，有中止條件
- [ ] 執行者記下了所有偏離（偏離不是過失，隱瞞才是）
- [ ] AI 沒有把「-18°C 通過」寫成「-20°C 通過」
- [ ] 簽認時寫明適用範圍（幾片樣板、哪些溫度點）

**常見失誤：** 用 AI 沙盒裡的檔案去燒錄，而不是 CI 產生的；量測沒達到條件卻沒記錄。

## 第 13 站　每週共讀共推會

| | |
|---|---|
| 目的 | 清決策、排優先序與資源、調整規則 |
| 誰 | 全員；協調人主持 |
| 開始前要有 | 議程（由 AI 依事實產生） |
| 完成條件 | 會議紀錄 MR 經與會者核准；會中的決定各自在 MR 留言 |
| 時間（假設） | 單一任務 30 分鐘；多任務的團隊會 45 分鐘（16 §9） |

**請 AI 準備議程：**

```text
請準備本週團隊會的議程，45 分鐘，分五段：逾期與卡住、跨任務碰撞、共用資源、
審查負荷、調整一條規則（見 docs/16 §9）。

資料只用 repo 與 MR 上的事實：
- 逾期或本週到期的決策請求
- 被阻擋的工作包與原因
- 範圍重疊、跨任務相依、介面契約的變更
- 人類任務佇列與需要的設備、人員
- 每個人的待審件數與等待最久的一件

每一項附連結。沒有資料的段落寫「無」，不要湊內容。
不要寫任何進度百分比；進度只列「已接受的工作包數／總數」。
另外列出本週前三大變更，各用兩句話說明主張與證據，供會上共讀。
```

**會後請 AI 起草紀錄：**

```text
會議結論如下：[貼上或口述結論]。

請依 kit/templates/sync-agenda.md 起草會議紀錄並開 MR。
- 只記錄我給你的結論，不要自行補充或推測沒談到的事。
- 會中做的決定，逐一列出「誰需要在哪個 MR 留言才生效」。
- 列出指派出去的人類任務、執行者與日期。
```

**人要確認：**
- [ ] 逾期的決策都指定了處理人
- [ ] 實體任務有排到具體的人與日期
- [ ] 這週有調整一條規則，並記下原因

**常見失誤：** 把會議開成逐項進度報告；會上說了算，卻沒在 MR 留下紀錄。

## 4. 本文的限制

- prompt 範例未經實測；不同的 Agent 與模型對同一段話的反應會不同，需依實際結果調整。
