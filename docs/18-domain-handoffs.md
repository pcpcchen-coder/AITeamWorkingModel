# 18 — 軟體、韌體、硬體的專屬交付範例

**文件狀態：** 範例草案 v0.7 · 2026-11-17
**搭配：** [17 十三站操作細則](17-station-guide.md)（通用的交付結構）、[交付 AI 的 Prompt](../prompts/handoff-prompts.md)（七個要素與常駐規則）、[10 領域規範](10-domain-profiles-sw-fw-hw.md)（各領域的自主度與驗證階梯）。
**本文補上：** 同樣的七個要素，在三個領域各要多說什麼、容易漏什麼。每個領域三個典型任務的交付範例。
**誠實聲明：** 案例、料號、數值皆為虛構。範例**尚未在真實專案上試用**。硬體部分另有一個未驗證的前提：AI 對實際 EDA 檔案的處理能力（10 §10），所以硬體範例一律以**匯出檔**（網表、BOM、PDF）為輸入。
**平台用語：** 以 GitLab 的 MR 為例；GitHub 上讀作 PR。

## 0. 三個領域各要多說什麼

| | 軟體 | 韌體 | 硬體 |
|---|---|---|---|
| AI 最容易做錯的事 | 改得比你要的多；用例外處理把錯誤吞掉 | 把主機端測試通過當成實機可用；常數沒有來源 | 把推論寫成設計；規格書數值記錯或編造 |
| 交付時一定要講 | 行為不變的範圍；公開介面能不能動 | 不碰實機；哪些只能在實機確認 | 你只提建議與檢查，由人定案；每個數值要有頁碼 |
| 證據的樣子 | 測試輸出、重現步驟 | 主機端測試、大小報告、目標編譯結果 | 計算腳本輸出、規格書引用、網表與 BOM 差異 |
| 最高能驗到 | V4（預備環境） | V3（模擬）；實機由人 | V3（模擬）；量測由人 |
| 審查者最該看 | 被改動的測試、錯誤處理、新增的相依 | 門檻與常數的來源、邊界與異常、中斷共用資料 | 假設清單、引用的頁碼、沒有依據的地方 |

每個領域的第一段是**加進專案 `AGENTS.md` 的領域補充規則**（接在 [`handoff-prompts.md` §2](../prompts/handoff-prompts.md) 的通用規則之後），之後是三個交付範例。

## 1. 軟體

### 1.1 領域補充規則（放進 `AGENTS.md`）

```markdown
### 軟體
- 只改這次任務需要的地方。看到順手可以改善的程式，寫進回報的「後續建議」，不要動。
- 修錯之前先寫出能重現問題的失敗測試，並保留它。
- 不用空的例外處理、預設值或重試把錯誤蓋掉。錯誤要被回報或明確處理。
- 公開介面、資料格式、設定檔格式的變更屬於 G2：停下來問。
- 新增相依套件前先說明必要性、授權與替代方案，等人決定。
- 效能相關的主張要附量測方式與數字；沒量就不要說「更快」。
- 不把憑證、個資或機密寫進程式、測試資料或日誌。
```

### 1.2 範例 S1：新增功能

情境：通訊訊框新增了故障旗標（WP-007 已合併），上位機要解析它，並在 SOH 計算中排除故障期間的資料。

```text
請執行 WP-021：上位機解析訊框的故障旗標，並在 SOH 計算中排除故障期間的資料。

【先讀】wp.md、knowledge/interfaces/protocol.yaml（版本 4，新增 fault_flags 欄位）、
sw/soh_demo/frame.py、sw/soh_demo/soh.py 與它們的測試。

【目的】
感測器斷線時韌體現在會回報故障。上位機若照常把那段資料算進 SOH，結果會偏掉。
我要確保故障期間的資料不參與計算，而且使用者看得出資料被排除了。

【範圍】
只能改 sw/soh_demo/** 與 sw/tests/**。不要改 protocol.yaml；訊框格式以它為準。

【要求】
- 解析邏輯要對照 protocol.yaml 的欄位定義，並新增或更新契約測試：
  介面契約改了而程式沒跟上時，測試要會失敗。
- 舊版訊框（沒有 fault_flags）要能照常處理；請說明你的相容作法並寫測試。
- 排除資料時要留下可查的紀錄（筆數、時間範圍），不要無聲丟棄。
- 測試要涵蓋：全部正常、部分故障、全部故障、旗標位元未定義的值。

【停下來問我】
- 你認為 protocol.yaml 的定義不夠用或有歧義。
- 「全部故障時 SOH 該回傳什麼」規格沒寫，請列選項問我，不要自己定。
- 需要新增相依套件。

【不要做】
重構不相關的程式；更動公開函式的簽名（需要的話先問）；為了讓舊測試通過而修改舊測試的期望值。

【完成後】
開 Draft MR，依樣板寫共讀包草稿。回報請包含：新增與修改了哪些測試、
舊版訊框的相容作法、你沒處理的情況。
```

### 1.3 範例 S2：修錯

情境：有人回報低溫時 SOH 偶爾出現負值。

```text
請處理 Issue #58：低溫時 SOH 偶爾出現負值。這是修錯任務，請依序做，不要跳步。

【先讀】Issue 的描述與附的資料片段、sw/soh_demo/soh.py、相關測試。

【第一步：重現】
先寫一個會失敗的測試重現問題。重現不出來就停下來告訴我你試了什麼，
不要憑猜測修改程式。

【第二步：找根因】
說明為什麼會出現負值，指出程式行號。請區分「根因」與「症狀出現的地方」。
如果根因在別的模組或在輸入資料，告訴我，不要只在輸出端把負值夾成零。

【第三步：修正】
- 修根因，改動越小越好。
- 不要用 max(0, x)、空的例外處理或預設值把症狀蓋掉。
- 保留第一步的測試；另外檢查同類的問題是否存在於其他換算函式，列出來但先不要改。

【範圍】sw/soh_demo/** 與 sw/tests/**。

【停下來問我】
根因其實是韌體送來的資料有問題；修正會改變其他情況下的輸出；需要改公開介面。

【完成後】
回報：重現步驟、根因（附行號）、修正內容、修正前後的測試輸出、
其他可能有同類問題的地方、你沒有驗證的情況。
```

### 1.4 範例 S3：重構（行為不變）

情境：溫度換算邏輯散在三個檔案，要抽成一個模組。屬於 G2（動到內部架構）。

```text
請執行 WP-024：把散在三個檔案的溫度換算邏輯抽成單一模組。這是「行為不變」的重構。

【先讀】wp.md、sw/soh_demo/ 下所有用到溫度換算的檔案與測試。

【目的】
三處實作有細微差異，之後改一處容易漏改另外兩處。我要它們共用同一份實作，
但這次不要改變任何對外行為。

【做法要求】
1. 動手前先盤點：列出三處實作的差異（四捨五入、邊界處理、單位）。
   差異本身可能是 bug，也可能是有意的；逐一列出來問我要保留哪一種，不要自己統一。
2. 我決定後，先補上能鎖住現有行為的測試，確認它們在重構前是通過的。
3. 再進行重構。重構後同一批測試必須不改一字就通過。
4. 公開函式的名稱與簽名保持不變；需要改請先問。

【範圍】sw/soh_demo/** 與 sw/tests/**。不新增相依套件。

【證據】
重構前與重構後各執行一次完整測試，兩次的輸出都要留存並登錄。

【完成後】
回報：差異盤點表與我的決定、新增的測試、重構前後的測試結果、
有沒有任何輸出在重構前後不同。
```

### 1.5 軟體：審查者最該確認

- [ ] 被修改或刪除的測試：改的是期望值，還是測試本身？理由成立嗎？
- [ ] 錯誤處理：有沒有新增的例外處理把問題蓋掉？
- [ ] 變更範圍：有沒有「順手」改到不相關的地方？
- [ ] 介面與資料格式：有沒有不在計畫內的變更？
- [ ] 新增的相依：有人同意過嗎？

## 2. 韌體

### 2.1 領域補充規則（放進 `AGENTS.md`）

```markdown
### 韌體
- 不執行、也不產生燒錄、除錯器連線、串列埠或儀器的指令。實機驗證是人的任務。
- 交給人燒錄的檔案必須由 CI 從已核准的版本產生，不使用你工作區裡的檔案。
- 每個門檻、校正常數、暫存器設定值都要註明來源（介面契約欄位、規格書或參考手冊
  的文件名、版次、頁碼，或已簽認的量測）。沒有來源就停下來問，不要填一個合理的值。
- 主機端測試與模擬的結果不能推論為實機行為。回報中固定列出「只能在實機確認的項目」。
- 處理數值時說明資料型別與範圍，檢查溢位、飽和、除以零、定點數的縮放。
- 中斷與主程式共用的資料要說明如何保護。
- 每次回報 Flash 與 RAM 用量及與上一版的差異；超過預算就停下來問。
- 保護功能、故障處理、看門狗、開機程序、記憶體配置、更新機制屬於安全關鍵：
  任何變更都要逐項填寫安全審查檢查表，並由合格審查者逐行審查。
- 介面契約（腳位、類比鏈、通訊、電源）不夠用或有矛盾時，停下來問，不要自己改或繞過。
```

### 2.2 範例 F1：數值處理（主機端可完整測試）

情境：ADC 取樣雜訊大，要加一個定點數的低通濾波器。

```text
請執行 WP-031：為溫度 ADC 取樣加上一階低通濾波器（定點數實作）。

【先讀】wp.md、fw/src/sensors/ 的現有程式、knowledge/interfaces/analog.yaml
（ADC 解析度與取樣率）。

【目的】
實機量測（EV-005-01）顯示溫度讀值有雜訊。我要在不引入浮點運算的前提下降低雜訊，
並且清楚知道濾波帶來的反應延遲。

【範圍】只能改 fw/src/sensors/** 與 fw/tests/**。

【要求】
- 濾波係數做成可設定的參數；預設值不要自己選，請列出候選值與各自的延遲、
  抑制效果，開決策請求讓我決定。
- 說明資料型別與每個中間值的範圍，證明不會溢位；測試要包含最大輸入、最小輸入、
  輸入劇烈跳變、長時間固定輸入後的殘差。
- 說明初始值怎麼設（第一筆取樣時輸出什麼），並測試。
- 感測器故障期間（WP-003 的錯誤碼）濾波器該怎麼處理，規格沒寫：列選項問我。
- 提供 Flash／RAM 用量與上一版的差異。

【只能在實機確認的項目】
請列出來（例如真實雜訊下的效果、執行時間），並起草一個給人執行的量測工作包建議。
不要用主機端的合成雜訊去下「雜訊已改善」的結論。

【完成後】開 Draft MR；回報照常駐規則的格式。
```

### 2.3 範例 F2：驅動與時序（最多驗到模擬）

情境：ADC 取樣由輪詢改為定時器觸發加中斷。屬於 G2。

```text
請執行 WP-033：ADC 取樣由主迴圈輪詢改為定時器觸發，轉換完成後以中斷讀取。

【先讀】wp.md、fw/src/drivers/adc.* 與現有測試、knowledge/interfaces/pinmap.yaml
與 analog.yaml、專案中已有的暫存器定義標頭檔。

【目的】
輪詢造成取樣間隔不固定，影響濾波器的行為。我要固定的取樣週期。

【這個任務的限制，請先讀清楚】
這類變更的正確性最終只能在實機確認。你能做到的是：程式、主機端可測的邏輯、
以及一份讓人能有效驗證的計畫。請不要宣稱時序正確。

【要求】
- 每個暫存器設定值註明依據：參考手冊的文件名、版次、章節與頁碼。
  你無法查證的設定值請標 UNKNOWN 並列出來，不要憑印象填。
- 把「硬體相依的薄層」與「可在主機端測試的邏輯」分開，後者要有單元測試
  （用替身模擬暫存器與中斷）。
- 列出中斷與主程式共用的所有資料，以及各自的保護方式。
- 說明中斷優先序的選擇理由，以及它與其他中斷的關係；不確定就列為問題。
- 列出取樣週期的預期值與允許誤差，供實機量測比對。

【交付給人的部分】
起草人類任務工作包：用示波器量取樣週期與抖動的程序書（依 human-task-record 樣板 A 段），
包含量測點、預期範圍、中止條件。你不操作任何設備。

【停下來問我】
需要更動腳位或介面契約；需要使用的周邊已被其他功能佔用；中斷優先序有衝突。

【完成後】
開 Draft MR。共讀包的主張中，凡涉及時序的一律標 HYPOTHESIS，並指向對應的量測工作包。
```

### 2.4 範例 F3：安全關鍵變更

情境：新增過溫保護的遲滯。門檻值已由人類決定（DR-031）。

```text
請執行 WP-035：過溫保護加入遲滯，避免在門檻附近反覆跳動。

這是安全關鍵變更（fw/src/protection/**）。完成後會由合格審查者逐行審查，
請把程式寫得容易審，而不是寫得精巧。

【先讀】wp.md、DR-031（門檻與遲滯值已由人決定：動作 60°C、解除 55°C）、
fw/src/protection/ 現有程式與測試、kit/checklists/fw-safety-review.md。

【要求】
- 門檻值只使用 DR-031 給的數值，並在程式中註明來源。你不可以調整數值；
  認為數值有問題就停下來問。
- 明確定義並測試每一種狀態轉換：正常→保護、保護→解除、開機時已超過門檻、
  感測器故障時（依安全原則：無法確認溫度時應視為不安全，請確認現有設計是否如此，
  不是的話停下來問）。
- 保護路徑不可依賴可能被阻塞的工作或通訊。請說明這條路徑的執行條件。
- 測試要涵蓋：剛好在門檻、門檻上下一個最小單位、在遲滯區間內來回、
  溫度讀值跳變、故障碼輸入。
- 不要修改或刪除現有的保護測試。現有測試若因為新行為而需要調整，逐一列出並說明。

【完成後】
- 逐項填寫 fw-safety-review 檢查表：每項寫結果與依據（行號、證據編號或頁碼），
  不可只打勾。你無法判定的項目寫「需人確認」。
- 列出只能在實機確認的項目，並起草量測工作包建議。
- 共讀包的必看清單要包含本次所有變更的行。
```

### 2.5 韌體：審查者最該確認

- [ ] 每個常數與門檻都有來源，而且來源是對的（抽查頁碼）
- [ ] 邊界、溢位、故障輸入有測試，不只正常範圍
- [ ] 共讀包有「只能在實機確認的項目」，且有對應的人類任務
- [ ] 沒有任何主張把主機端結果寫成實機結論
- [ ] 安全關鍵變更：檢查表每項有依據；合格審查者逐行看過
- [ ] Flash／RAM 在預算內

## 3. 硬體

### 3.1 領域補充規則（放進 `AGENTS.md`）

```markdown
### 硬體
- 你的角色是分析、檢查與起草。電路圖、佈局、BOM 的變更由人定案；
  你提出的變更在人確認前都是 RECOMMENDATION。
- 規格書的每個數值都要附文件名、版次、頁碼與適用條件（溫度、電壓、頻率）。
  找不到就寫 UNKNOWN。不憑記憶引用規格，不外推表格範圍以外的數值。
- 計算寫成可重跑的腳本，輸入參數逐一註明來源，並列出所有假設。
- 模擬結果最高為 OBSERVED，不能單獨支持「硬體已驗證」。說明模型的來源與限制。
- 你以匯出檔（網表、BOM、PDF）為輸入。圖面與匯出檔不一致時，以人的說法為準並回報。
- 佈局、電磁相容、散熱的最終判斷超出你能可靠判斷的範圍：可以列出疑慮與檢查項，
  但要明說這需要人與量測確認。
- 不產生製造輸出、不下單、不操作任何設備。上電、量測、改板、送板、採購是人的任務。
- 涉及高電壓、大電流、高能量或電池的操作，一律以實驗室的安全 SOP 為準；
  你起草的程序不取代 SOP。
```

### 3.2 範例 H1：元件選型研究

情境：現用的 NTC 停產，要找替代料。

```text
請執行 WP-041：為停產的 NTC（現用料號見 BOM 的 RT1）研究替代料，提出比較與建議。
這是研究任務：你提供資料與建議，選哪一顆由我和硬體負責人決定。

【先讀】wp.md、hw/bom/ 的 BOM 匯出檔、knowledge/interfaces/analog.yaml、
WP-002 的誤差分析、docs/datasheets/ 下已有的規格書。

【候選來源】
我放了三份候選料的規格書在 docs/datasheets/candidates/。只用這三份與現用料的規格書；
不要引用你記憶中的其他料號或數值。

【要比較的項目】
R25 與容差、B 值與容差、R-T 表涵蓋的溫度範圍、操作溫度範圍、封裝與腳位、
熱時間常數、自熱（耗散常數）。

【要求】
- 每個數值附：文件名、版次、頁碼、適用條件。規格書沒寫的填 UNKNOWN。
- 不要外推：R-T 表沒涵蓋到 -20°C 的，就寫「表格未涵蓋」，不要用 B 值公式算一個填進去
  ——可以另外標示為「以 B 值估算」並註明這是估算。
- 用 WP-002 的計算腳本，以各候選料的參數重跑最壞情況誤差，輸出留存。
- 列出換料對其他地方的影響：韌體查表要不要重產、封裝是否相容、
  介面契約哪些欄位要改。
- 供應狀況、生命週期、價格你無法查證，請列為「需人確認」，不要推測。

【完成後】
交一份比較表、各候選的最壞情況誤差、你的建議與理由、所有 UNKNOWN 與假設清單。
建議標 RECOMMENDATION。開決策請求讓我們選。
```

### 3.3 範例 H2：電路圖與 BOM 變更的檢查（AI 當檢查者）

情境：硬體負責人已經改好電路圖（上拉電阻 10k→22k，並加了一顆濾波電容），請 AI 做第一輪檢查。

```text
硬體負責人已完成電路圖變更（MR !52）。請你當第一輪檢查者。
你不修改任何圖面或 BOM；只提出發現，由人判斷。

【輸入】
hw/export/ 下這次與上一版的匯出檔：網表、BOM、電路圖 PDF；變更說明在 MR 描述；
knowledge/interfaces/pinmap.yaml、analog.yaml；kit/checklists/ 的電路圖審查檢查表（若有）。

【請檢查】
1. 網表差異：列出新增、移除、改接的網路與元件。與 MR 描述的變更是否一致？
   有沒有描述沒提到的差異？
2. BOM 差異：值、封裝、料號的變更；有沒有與圖面不一致。
3. 與介面契約的一致性：腳位、上拉值、參考電壓是否與 pinmap.yaml、analog.yaml 相符；
   不符的逐項列出（可能是圖面要改，也可能是契約要更新，由人決定）。
4. 新增元件的額定值：依規格書（docs/datasheets/）檢查耐壓、功率、溫度的降額；
   沒有規格書的寫 UNKNOWN。
5. 這次變更對其他電路的影響：共用同一節點或同一電源軌的電路有哪些。
6. 韌體需要跟著改的地方：依賴被改動數值的常數與查表。

【每項發現請寫】
位置（網路名或元件編號）、你看到什麼、為什麼可能是問題、依據、
你的把握（高／中／低）。把握低的也要列，但標清楚。

【你做不到的事，請直接說】
佈局、走線、電磁相容、散熱的問題，無法從這些匯出檔可靠判斷；
PDF 與網表不一致時你無法得知哪一個是對的。

【完成後】
把發現寫成 MR 上的審查意見草稿交給我，由我決定哪些要貼上去。
你的檢查不構成核准。
```

### 3.4 範例 H3：首次上電程序書（人執行）

情境：改版樣板回來了，要準備第一次上電的程序。屬於 G3，由合格人員執行。

```text
請為改版樣板（硬體版本 A2）準備首次上電的程序書與紀錄表，
依 kit/templates/human-task-record.md 的 A 段。

執行者是合格人員。你不操作任何設備。這份程序會由合格人員與我審閱後才啟用，
並以實驗室安全 SOP 為準。

【先讀】hw/export/ 的電路圖 PDF 與網表、knowledge/interfaces/power.yaml（電源軌與
上電順序）、上一版樣板的上電紀錄（若有）、kit/checklists/ 的上電檢查表（若有）。

【程序必須包含】
- 上電前的目視與靜態檢查：要看什麼、要量哪些點對地的電阻、預期範圍。
- 限流供電的分段步驟：每一段的電壓與限流設定、停留多久、要量哪些測試點。
- 每個量測點的預期值與允許範圍，並註明依據（電路圖頁碼、power.yaml 的欄位、
  規格書頁碼）。你算不出或沒有依據的預期值寫「待執行者確認」，不要填一個數字。
- 明確的中止條件：電流超過多少、哪個電壓超出範圍、任何發熱或異味——立即斷電並記錄。
- 每一步要記錄的欄位，包含儀器型號與校正編號、環境條件。
- 上電成功之後才進行的下一步（例如燒錄），以及燒錄要用的檔案：
  必須是 CI 由已核准版本產生的，附檔名與雜湊。

【要求】
- 步驟寫成一步一個動作，讓執行者不需要推測。
- 把你做的假設集中列在程序最前面（例如「假設使用可設定限流的桌上型電源」）。
- 板上有任何高電壓、大電流或電池相關的部分，請在最前面標示，並寫明
  「本節依實驗室安全 SOP 執行」，不要自己寫安全步驟來取代 SOP。

【完成後】
開 MR 並開啟動核准的決策請求（需要我與合格人員兩人核准）。
列出你最不確定的三個預期值。
```

## 4. 跨領域：介面契約變更

三個領域最常見的失敗是「兩邊對介面的理解不同」。動到介面契約時用這個交付，不論是哪一方發起：

```text
請執行 WP-050：通訊訊框的溫度欄位解析度由 0.1°C 改為 0.01°C。
這是介面契約變更（G2 跨領域），會同時影響韌體與上位機。

【先讀】knowledge/interfaces/protocol.yaml、韌體的訊框編碼、上位機的解析、
兩邊的契約測試、角色矩陣。

【這一步只做影響分析，不要改任何程式】
1. 列出契約要改的欄位（型別、縮放、範圍、版本號）。
   數值範圍會不會超出原欄位的型別？
2. 列出韌體與上位機各有哪些檔案與測試受影響。
3. 相容性：新舊版本混用時會發生什麼（新韌體配舊上位機、舊韌體配新上位機）？
   列出可行的過渡作法與各自的代價。
4. 需要哪些領域負責人核准（依角色矩陣）。
5. 建議怎麼拆工作包與先後順序，讓每一步合併後系統都還能運作。

【完成後】
交影響分析與決策請求（過渡作法由人選）。等介面兩側的負責人都同意後，
我會再分別交付契約、韌體、上位機的工作包。
```

## 5. 這些範例的共同寫法

回頭看九個範例，每個領域都用了同樣幾招，可以直接套到你自己的任務：

| 寫法 | 例子 | 用意 |
|---|---|---|
| 先說這個任務的天花板 | 「這類變更的正確性最終只能在實機確認」 | 讓 AI 不會過度宣稱 |
| 把「數值由誰決定」講明 | 「門檻值只使用 DR-031 給的數值」 | 數值是決定，不是實作細節 |
| 列出規格沒寫的地方並要求發問 | 「全部故障時該回傳什麼，規格沒寫」 | 你想得到的空白先點出來 |
| 限定資料來源 | 「只用這三份規格書」 | 防止憑記憶引用 |
| 要求先盤點再動手 | 「先列出三處實作的差異」 | 把隱藏的決定變成明示的 |
| 要求說出做不到的事 | 「你做不到的事，請直接說」 | 得到誠實的邊界 |
| 把人的任務一併起草 | 「起草量測工作包建議」 | 接力不斷線 |

## 6. 本文的限制

- 九個範例皆未經實測；不同的 Agent 與模型反應會不同。
- 硬體範例假設能取得網表、BOM、PDF 的匯出檔；若單位的 EDA 無法匯出，H2 需要重新設計。
- 檢查表目前只有韌體安全與硬體釋出兩份（`kit/checklists/`）；範例中提到的電路圖審查、上電檢查表尚未撰寫，所以寫了「若有」。
- 範例中的安全相關步驟都以實驗室 SOP 為準；本文不提供、也不取代安全程序。
