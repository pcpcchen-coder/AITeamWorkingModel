# 10 — 領域規範：軟體／韌體／硬體的 AI 開發邊界與證據

**文件狀態：** 設計提案 v0.3 · 2026-11-13
**前提：** 流程本體見 [09](09-execution-playbook.md)。本文回答：同一套流程套到三種領域時，**AI 可以做到哪、要什麼證據、哪些一定要人**。
**誠實聲明：** AI 在硬體設計上的實際能力尚未在本專案驗證；本文對硬體採保守預設，需以試點結果調整。工具名稱均為候選，實作前須核對版本與授權。

## 1. 為什麼三個領域不能用同一把尺

| 面向 | 軟體 | 韌體 | 硬體 |
|---|---|---|---|
| 修正成本 | 低（再 commit） | 中（重新燒錄；現場更新成本高） | 高（改版、重新打樣，數週） |
| 可自動驗證比例 | 高 | 中（主機端可測；時序與周邊需實機） | 低（計算與模擬可自動；最終靠量測） |
| 失敗後果 | 多為功能錯誤 | 可能損壞硬體或失去保護功能 | 可能有電氣／熱／人身危害 |
| 可 diff 的程度 | 完整文字 diff | 文字 diff + 二進位大小／配置差異 | 需圖像 diff；網表與 BOM 可文字比對 |
| AI 自主度上限（預設） | A2–A3 | 主機端 A2；實機 A1 | 分析 A2–A3；圖面 A2（人逐項審）；實體 A1／A0 |

結論：**流程相同，但驗證階梯、證據種類、Gate 門檻與審查深度依領域而異**，由「領域包」（domain pack）提供。

## 2. 共通：驗證階梯

每個領域都有一條由便宜到昂貴的驗證階梯。AI 可自主爬到某一階，再往上必須換人。

| 階 | 軟體 | 韌體 | 硬體 | 誰執行 |
|---|---|---|---|---|
| V1 靜態 | lint、型別、相依掃描 | 靜態分析、編碼規範子集、可為目標編譯 | ERC／DRC、BOM 規則檢查 | AI + CI |
| V2 單元／計算 | 單元測試 | 主機端單元測試（周邊以替身模擬） | 計算腳本（容差、降額、最壞情況） | AI + CI |
| V3 整合／模擬 | 整合測試、契約測試 | 模擬器／SIL、協定層測試 | 電路模擬（SPICE 類）、熱估算 | AI + CI |
| V4 實機受控 | 預備環境 | **開發板 HIL** | **打樣板首次上電與量測** | **人**（AI 準備與分析） |
| V5 真實條件 | 正式環境 | 產品硬體、長時間／邊界條件 | 環境測試、安規／EMC | **人**，G3 |

規則：**共讀包必須寫明每條主張爬到第幾階**。只到 V2 的結論不可寫成「已驗證可用於實機」。

## 3. 軟體領域包

**AI 自主範圍：** 在分支與沙盒內分析、實作、測試、重構、文件。

| 活動 | 自主度 | Gate | 必要證據 |
|---|---|---|---|
| 文件、分析腳本、內部工具 | A3 | G0 | lint 通過 |
| 一般功能與修錯 | A2 | G1 | 單元／整合測試紀錄、覆蓋差異 |
| 公開 API／資料格式／架構／相依新增 | A2 | G2 | 上述 + 契約測試 + ADR |
| 安全、權限、機密處理相關 | A2 | G2 + 指定 Reviewer | 上述 + 安全檢查表 |
| 正式部署、對外發布 | A1 | G3 | 發布檢查表、回退演練紀錄 |

**審查重點（必看規則追加）：** 新增相依、權限判斷、資料遷移、錯誤處理被吞掉的地方、測試被修改之處。

## 4. 韌體領域包

**AI 自主範圍：** 原始碼、建置設定、主機端測試、模擬器測試、大小與資源分析。**不可**：對任何實體目標燒錄、開啟除錯器連線、操作串列埠或儀器。

| 活動 | 自主度 | Gate | 必要證據 |
|---|---|---|---|
| 演算法、資料轉換、協定解析（可在主機端完整測試者） | A2 | G1 | 主機端單元測試、靜態分析、目標編譯成功、大小報告 |
| 驅動、中斷、時序相關 | A2（至 V3） | G2 | 上述 + 模擬器測試（若可行）+ **標明未經實機驗證** |
| **安全關鍵**：保護門檻、故障處理、看門狗、開機程序、記憶體配置、更新機制 | A2（至 V3） | G2 + 合格 Reviewer 逐行 | 上述 + 安全審查檢查表 + 門檻值來源引用 |
| 腳位／暫存器／通訊介面定義變更 | A2 | G2 跨領域（硬體與韌體 owner 都要核准） | ICD 差異 + 兩側影響分析 |
| 開發板 HIL 測試 | **A1** | G3（啟動核准） | 燒錄檔雜湊、板號、接線、測試腳本、原始 log、執行者簽名 |
| 產品硬體燒錄／釋出版本 | **A1／A0** | G3 | 釋出檢查表、版本與雜湊、回退方式 |

**韌體特有證據欄位：**

- 建置產物雜湊（ELF／HEX 的 sha256）、工具鏈版本、編譯選項。
- Flash／RAM 用量與相對上一版的差異，對照預算上限。
- HIL 紀錄：板號、硬體版本、燒錄檔雜湊、儀器與校正編號、環境條件。

**硬性規則：**

1. 門檻與校正常數不可寫死而無來源；每個數值要引用規格書頁碼或已簽認的量測。
2. 「主機端測試全過」≠「實機可用」。共讀包需列出**只能在實機驗證的項目清單**，並產生對應的人類任務 WP。
3. 交給人燒錄的二進位檔，必須是 CI 由已核准 commit 重建的產物，不是 Agent 沙盒內的檔案。

## 5. 硬體領域包

**AI 的角色定位（保守預設）：分析者、檢查者、起草者；不是定案者。**

| 活動 | 自主度 | Gate | 必要證據 |
|---|---|---|---|
| 需求整理、誤差／功率／熱預算分析 | A3 | G0–G1 | 計算腳本 + 輸出、假設清單 |
| 元件選型研究、規格書參數擷取 | A2 | G1 | **每個參數附規格書名稱、版次、頁碼**；無來源標 UNKNOWN |
| 最壞情況／容差／降額計算 | A2 | G1 | 可重跑的腳本、輸入參數來源 |
| 電路模擬 | A2 | G1 | 網表雜湊、模型來源、模擬設定、結果 |
| 電路圖變更**建議**（由 AI 提出差異，人確認後成為正式圖面） | A2 | G2 | ERC 報告、網表差異、圖像差異、設計審查檢查表 |
| BOM 變更 | A2 | G2 | BOM 差異、替代料／生命週期／降額檢查 |
| PCB 佈局 | **A0**（AI 只做 DRC 與檢查表） | G2 | DRC 報告、圖像差異、佈局審查檢查表 |
| 製造釋出（輸出製造檔、送板） | **A0／A1** | **G3 + R3 會議** | 釋出檢查表全項簽認、輸出檔雜湊、兩位人類核准 |
| 採購 | **A1** | G3 | 核准的 BOM 版本 |
| 首次上電、量測、調機 | **A1** | G3（啟動核准） | 上電程序書、安全檢查表、量測紀錄、原始資料雜湊 |
| 高壓／大電流／高能量測試 | **A0** | G3 + 機構安全規範 | 依機構 SOP；本流程不取代 SOP |

**硬體特有證據欄位：**

- 規格書引用：文件名、版次、頁碼、擷取值、條件（溫度、電壓）。
- 量測紀錄：待測物編號與硬體版本、儀器型號與校正編號、探棒／接線、環境條件、原始資料檔雜湊、執行者。
- 圖面版本：電路圖／佈局檔的 commit、輸出圖像的雜湊。

**硬性規則：**

1. AI 提出的電路變更在人類確認前是 RECOMMENDATION，不是設計。
2. 模擬結果最高只能是 OBSERVED（模擬），**不可**單獨支持「硬體已驗證」；需搭配量測。
3. 釋出是不可逆動作：採 R3 會議審查，不走純非同步 PR。
4. 原始量測資料量大時不進 Git，只登錄 manifest（位置、雜湊、條件）；公開 repo 永不放真實量測。

**候選工具（需實測）：** 文字格式 EDA（如 KiCad）搭配其命令列做 ERC／DRC／輸出；開源電路模擬器；圖像差異工具。若單位使用封閉格式 EDA，則以「匯出網表／BOM／PDF 進版控」作為 AI 可讀的替代來源——此為待確認條件（見 08）。

## 6. 跨領域：介面契約（ICD）是軟硬韌的共同正本

軟硬韌最常見的失敗是「兩邊對介面的理解不同」。作法：**把介面寫成機器可讀的單一正本**，三方都從它產生或核對。

位置：`knowledge/interfaces/`

| 檔案 | 內容 | 使用者 |
|---|---|---|
| `pinmap.yaml` | MCU 腳位 ↔ 網路名稱 ↔ 功能 ↔ 電氣限制 | 硬體核對電路圖；韌體產生腳位定義 |
| `analog.yaml` | 類比鏈參數：分壓、增益、參考電壓、ADC 解析度 | 硬體計算；韌體轉換常數；軟體換算 |
| `protocol.yaml` | 通訊訊框、欄位、單位、縮放、版本 | 韌體與上位機雙方的編解碼與契約測試 |
| `power.yaml` | 電源軌、上電順序、電流預算 | 硬體設計；韌體低功耗策略 |

規則：

- 任何 ICD 變更 = **G2 跨領域**：受影響領域的 owner 都必須核准；共讀包必須有「各領域影響」段落。
- CI 檢查一致性：韌體常數與軟體換算是否與 ICD 相符（由 ICD 產生或以測試比對）。
- 需求追溯（輕量）：`knowledge/requirements.yaml` 定義需求編號；WP 以 `satisfies` 連結；工具產生「需求 ↔ WP ↔ 證據 ↔ 驗證階」矩陣，一眼看出哪些需求只驗到模擬。

## 7. 預設路徑政策（示意）

policy 以路徑樣式決定最低 Gate 與加簽角色。以下為領域包提供的預設值，專案可調嚴、不可由 AI 調鬆。

```yaml
# .aiteam/policy.yaml（節錄示意）
paths:
  - match: "docs/**"
    domain: sys
    min_gate: G0
  - match: "sw/**"
    domain: sw
    min_gate: G1
  - match: "fw/src/**"
    domain: fw
    min_gate: G1
  - match: "fw/src/protection/**"
    domain: fw
    min_gate: G2
    safety_critical: true
    extra_approver_role: safety_reviewer
  - match: "fw/boot/**"
    domain: fw
    min_gate: G2
    safety_critical: true
  - match: "hw/calc/**"
    domain: hw
    min_gate: G1
  - match: "hw/schematic/**"
    domain: hw
    min_gate: G2
  - match: "hw/release/**"
    domain: hw
    min_gate: G3
  - match: "knowledge/interfaces/**"
    domain: sys
    min_gate: G2
    cross_domain: [hw, fw, sw]
  - match: ".aiteam/**"
    human_only: true
```

## 8. 人類任務（實體動作）的標準程序

所有 A1 活動共用同一種紀錄，樣板見 [`kit/templates/human-task-record.md`](../kit/templates/human-task-record.md)：

| 階段 | 內容 | 誰 |
|---|---|---|
| 準備 | 目的、對應驗收條件、待測物與版本、設備與接線、步驟、預期範圍、**中止條件**、空白紀錄表 | AI 起草 |
| 核准 | 檢查程序與安全檢查表；確認執行者具資格 | 合格人類（G3 啟動核准） |
| 執行 | 照程序操作；紀錄實際條件、讀值、偏離與異常；保存原始資料 | 合格人類 |
| 分析 | 比對預期、不確定度、是否滿足驗收條件；標示 OBSERVED | AI |
| 簽認 | 依原始資料確認結論，升為 VERIFIED 或退回 | Reviewer（非執行者為佳） |

AI 起草的程序書**不取代**機構安全 SOP；兩者衝突時以 SOP 為準並回報衝突。

## 9. 各領域審查檢查表

領域包提供檢查表，審查時逐項勾選並隨 PR 留存：

- 韌體安全關鍵審查：[`kit/checklists/fw-safety-review.md`](../kit/checklists/fw-safety-review.md)
- 硬體釋出（G3）：[`kit/checklists/hw-release-g3.md`](../kit/checklists/hw-release-g3.md)
- 其餘（軟體安全、電路圖審查、佈局審查、上電程序）由工單 K5 補齊（見 13）。

檢查表的每一項需填「通過／不適用／不通過」與**證據編號或頁碼**；不可只打勾。

## 10. 尚待以試點回答的問題

1. AI 對本單位實際使用的 EDA 檔案能讀寫到什麼程度？圖像差異是否足以支援人類審查？
2. 韌體有多少比例的驗收條件可在主機端或模擬器完成？
3. HIL 是否可由受控測試架自動執行（屆時自主度可由 A1 調整，但需另行資安與安全審核，對應 07 的 T12）？
4. 硬體審查會議（R3）在 AI 準備檢查表後，實際需要多少時間？
5. 哪些量測可以用既有資料回放，降低人類任務的數量？
