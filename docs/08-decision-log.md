# 08 — 討論整合、設計決策與待確認問題

**版本：** 2026-11-13 · 目的：將需求演變與目前已採納的設計假設固定在 Repo，避免新接手的人只看到單一技術方案、不理解原因。

## 1. 需求演進

| 階段 | 原問題 | 解決方向 | 保留價值 |
|---|---|---|---|
| A：單人研發 | 每位工程師獨自負責項目，人員異動時技術難交接 | Primary + Backup、共同資產 | 技術不再只依賴個人 |
| B：減少備援負擔 | Backup 不可能同步追逐全部細節 | AI Shadow 持續整理差異、問答與接手包 | 平常低負擔但保持進入能力 |
| C：本地 LLM | 研究單位有機密與持續推論成本考量 | 內網優先、模型可替換、權限限定 | 避免上層工作流綁特定 AI SaaS |
| D：AI 主動研發 | 如果 AI 已可執行程式與分析，人類是否仍應主導每個步驟？ | **AI-Driven R&D + Human Co-Review** | AI 在授權範圍內推進，人類負責方向、審核與決策 |
| E：可操作化（v0.3） | 原則與平台藍圖都有了，但明天要怎麼開始做？軟韌硬的界線在哪？ | **Git-native Operating Kit** + 領域規範 + 共推協定 | 不等平台即可運作；用真實使用數據決定平台規模 |

**目前以 D 為主設計；A–C 成為 D 的基礎能力，不各自建立孤立系統。**

## 2. 已採用的架構決策（Proposal / ADR 草案）

### ADR-001：以「AI 主導執行、人類共同監督」為目標模式

- 決策：由 AI Project Lead 分派 Research / Engineer / Validator / Handover 任務。
- 理由：將人類時間集中於研究問題設定、技術判斷、挑戰假設及風險控制。
- 邊界：重大決策、安全與實體設備操作必須保留人類權限。

### ADR-002：Backup 的任務是「維持接手能力」，不是第二位平行開發者

- 決策：週摘要 + 共讀 + 每月獨立演練；L0–L3 以測試證據評級。
- 理由：避免雙倍投入，又不能只依 AI 文字判斷能力。
- 風險：備援可能只會使用 AI 工具而不具判斷能力；需安排能解釋異常的真實任務。

### ADR-003：研究成果是多人共讀的 versioned artifact

- 決策：研究備忘、模型結果、PR、實驗波形皆可以評論、要求修改與正式核准。
- 理由：Chat 對話不適合保存跨人員的決策與可追溯技術事實。
- 待細化：波形圖與模型可視化如何錨定評論到特定資料段。

### ADR-004：本地模型執行與業務系統分離

- 決策：推論層採 OpenAI-compatible adapter；Ollama 起步，達到量化需求再增加 vLLM / gateway。
- 理由：模型更新快速，任務與資料模型不應隨推論工具更換。
- 風險：本地 LLM 長上下文/工具使用/併發能力需要實機 benchmark。

### ADR-005：正式事實以原始證據為準

- 決策：Source of Truth 是 Git、Issue、ADR、實驗 manifest、測試證據。
- 理由：摘要易遺漏與誤讀，RAG 索引可重建。
- 邊界：沒有證據 → UNKNOWN / HYPOTHESIS；不能偽裝 VERIFIED。

### ADR-006：自動化先走低風險沙盒

- 決策：模型可自主分析、起草 PR、執行授權測試；不得自行對實體設備或正式環境做未授權變更。
- 理由：研究單位同時包含軟體與物理系統，風險不同。
- 下一步：和機構安全/IT/實驗室主管定義實際 permission matrix。

### ADR-007：不要自製通用聊天平台

- 決策：Open WebUI 類通用入口可部署現成產品，自己專注於 Mission Control / Co-Review / Takeover。
- 理由：自製價值在研發狀態與驗證流程，不在重做聊天 UI。
- 風險：資料分散、權限不一致；正式狀態須集中於受控 API/DB。

### ADR-008：流程先在 Git 上運作，平台是之後的檢視層（v0.3）

- 決策：任務、證據、決策以版控檔案表示；PR 為共讀面；CI 為關卡；以確定性 CLI（`aitw`）操作。
- 理由：不需後端即可開始；檔案可稽核、可搬遷；平台日後讀同一份資料。
- 風險：檔案與欄位造成流程負擔；需以工具與 Agent 代填並以指標檢視。
- 影響：07 的平台層工單延後，T04–T10 由 Kit 先行滿足。

### ADR-009：人類核准的正本是 forge 上的已驗證行為（v0.3）

- 決策：核准＝授權人類針對特定 commit 的 PR review 或留言；檔案內的決議欄位只是指標，由 Gate 回查。
- 理由：滿足 05 §4「核准綁定身份與版本、不可由 Agent 偽造」，且不需自建身份系統。
- 邊界：Agent 需使用獨立的機器身份；不防範具管理權限者的惡意行為。

### ADR-010：VERIFIED 只能來自 CI 重跑或人類簽認（v0.3）

- 決策：Agent 自行產生的證據最高為 OBSERVED；模擬結果最高為 OBSERVED。
- 理由：防止 AI 自證與形式化證據；讓標籤對審查者有實際意義。

### ADR-011：軟／韌／硬採不同自主度；實體動作一律由人執行（v0.3）

- 決策：定義 A0–A3 與 V1–V5；燒錄、上電、量測、送板、採購為「人類任務」，AI 準備程序並分析紀錄。
- 理由：三個領域的修正成本、可自動驗證比例與失敗後果不同。
- 待驗證：AI 對實際 EDA 檔案的處理能力；硬體採保守預設。

### ADR-012：介面契約（ICD）為軟韌硬的共同正本（v0.3）

- 決策：腳位、類比鏈、通訊、電源以機器可讀檔案維護；任何變更為 G2 跨領域，受影響領域的 owner 都需核准。
- 理由：跨領域最常見的失敗是雙方對介面理解不同。

### ADR-013：以 WIP 上限與審查分級保護人類注意力（v0.3）

- 決策：審查層級 R0–R3、必看清單由 policy 規則產生、每人待審上限、決策時限與升級；不採「逾期視為同意」。
- 理由：AI 產出速度高於人類審查速度，瓶頸在人。
- 待驗證：各上限與時間假設需以試點數據調整。

### ADR-014：GitLab 為一等公民平台；以既有案例為首個試點（v0.4）

- 背景：單位已有案例採「AI 執行開發、同仁在 GitLab 上 review」，運作良好。
- 決策：流程與檔案契約維持平台中立；Forge 整合同時提供 GitHub 與 GitLab。真實試點以 GitLab 為優先，採 14 §6 的漸進導入階梯，從 MR 樣板與看板 label 開始。
- 理由：沿用同仁已熟悉的平台與習慣，導入阻力最低；自架 GitLab 也符合機密資料的需求。
- 關鍵發現：GitLab Free 的核准不擋合併，需由 CI 中的 Gate job 強制；MR pipeline 使用來源分支的 CI 設定，須把 CI 設定檔移到 AI 無法寫入的獨立專案。
- 待確認：GitLab 版本與授權等級、AI 的提交身份、現行 review 規則（14 §8）。

## 3. 尚未決定、需要實際盤點的條件

1. 研究團隊有多少人、平均同時多少專案、多少會同時使用模型？
2. 可使用的本地 GPU / RAM / 儲存資源與 IT 安全管制？
3. 現有 Git / Issue / NAS / ELN / 實驗儀器系統為何？是否已有 API？
4. 是否允許研究資料進入本地 LLM；不同資料分級的保留政策？
5. 重要研究結論的最終簽核者與實驗設備安全責任怎麼定義？
6. Project Portfolio KPI 要與既有 PM 系統整合或建立獨立看板？
7. 跨部門專家能否擔任 Backup？是否有正式演練時間/績效配額？

8. （v0.3）Forge 平台、Agent 的機器身份、EDA 與韌體工具鏈、真實專案存放位置等，見 [13 §6](13-opus-handoff.md) 的 D1–D8。

這些未定項必須作為下一輪的需求訪談與 PoC 輸入，**不可在程式或部署文件中默認已有答案**。

## 4. 第一個 PoC 的具體問題

> 「在一個有版控資料、真實工作與兩位參與者的試點中，AI 能否持續推進至少一個低風險研發任務，讓 Primary / Backup 共讀有來源的成果，且 Backup 在不詢問 Primary 的情況下重現一個可驗證結果？」

成功所需證據：
- 任務的範圍、核准權與驗收條件。
- AI 工具操作及模型版本的實際 trace。
- 具 revision/source ID 的輸出與驗證記錄。
- Primary/Backup review 的決策歷程。
- Backup 獨立操作紀錄及通過／失敗原因。
- 人力工時與錯誤率相對既有流程的比較。

## 5. 外部研究與產品驗證原則

本 Repo 的工具名稱與模型僅代表候選技術。準備導入前應重新核對模型權重／授權、工具版本、OS/GPU 支援、網路行為與資安規範。勿將先前討論中的價格、模型效能或版本當作永久有效資訊。
